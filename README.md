# Event Manager

Учебный REST API для создания событий и управления их бронированиями на ASP.NET Core.

## Запуск

Для запуска нужны .NET SDK 10 и доступный сервер PostgreSQL.

В `EventManager.Api/appsettings.json` настройте `ConnectionStrings:DefaultConnection`:

```json
{
  "ConnectionStrings": {
    "DefaultConnection": "Host=localhost;Port=5432;Database=eventapi;Username=postgres;Password=postgres"
  }
}
```

Укажите адрес сервера, имя базы и учётные данные своей PostgreSQL. Строку подключения также можно переопределить переменной окружения `ConnectionStrings__DefaultConnection`.

При запуске `EnsureCreated` автоматически создаёт базу и таблицы `events` и `bookings`, если схема ещё не существует. Пользователь PostgreSQL должен иметь права на создание необходимых объектов. Метод не обновляет существующую схему и не применяется вместе с миграциями.

События и бронирования хранятся в PostgreSQL через Entity Framework Core и сохраняются после перезапуска приложения.

```powershell
dotnet run --project .\EventManager.Api\EventManager.Api.csproj
```

После запуска Swagger UI будет доступен по адресу:

```text
http://localhost:5239/swagger
```

Если порт переопределён в настройках запуска, его актуальное значение отображается в консоли приложения.

## API

Базовый путь: `/events`.

| Метод | Путь | Описание | Успешный ответ |
|---|---|---|---|
| `GET` | `/events` | Получить список событий | `200 OK` |
| `GET` | `/events/{id}` | Получить событие по идентификатору | `200 OK` |
| `POST` | `/events` | Создать событие | `201 Created` |
| `POST` | `/events/{id}/book` | Создать бронь для события | `202 Accepted` |
| `PUT` | `/events/{id}` | Полностью обновить событие | `200 OK` |
| `DELETE` | `/events/{id}` | Удалить событие | `204 No Content` |
| `GET` | `/bookings/{id}` | Получить состояние брони | `200 OK` |

Если событие с указанным идентификатором не найдено, `GET`, `PUT`, `DELETE` и создание брони вернут `404 Not Found`. Получение несуществующей брони также вернёт `404 Not Found`. Попытка забронировать место на заполненном событии вернёт `409 Conflict`.

### Модель события

Модель события содержит два поля вместимости:

| Поле | Тип | Описание |
|---|---|---|
| `totalSeats` | `integer` | Общее количество мест. Задаётся при создании события и должно быть больше нуля. |
| `availableSeats` | `integer` | Текущее количество свободных мест. Изначально равно `totalSeats`, уменьшается при бронировании и восстанавливается при отклонении брони. |

### Фильтрация и пагинация

`GET /events` поддерживает параметры строки запроса:

| Параметр | Тип | Значение по умолчанию | Описание |
|---|---|---|---|
| `title` | `string` | — | Часть названия события без учёта регистра |
| `from` | `date-time` | — | Минимальные дата и время начала события включительно |
| `to` | `date-time` | — | Максимальные дата и время окончания события включительно |
| `page` | `integer` | `1` | Номер страницы, начиная с 1 |
| `pageSize` | `integer` | `10` | Количество событий на странице, минимум 1 |

Параметры фильтрации можно комбинировать. Например:

```http
GET /events?title=workshop&from=2026-09-01T00:00:00Z&to=2026-09-30T23:59:59Z&page=1&pageSize=10
```

Ответ содержит отфильтрованные события и данные пагинации:

Коллекция возвращается в `items`, количество страниц — в `totalPages`.

```json
{
  "totalCount": 1,
  "items": [
    {
      "id": "66a1ed2f-a302-4441-a228-559f328bbe5e",
      "title": "Воркшоп по ASP.NET Core",
      "description": "Практика разработки Web API.",
      "startAt": "2026-09-19T11:00:00Z",
      "endAt": "2026-09-19T14:00:00Z",
      "totalSeats": 30,
      "availableSeats": 30
    }
  ],
  "page": 1,
  "pageSize": 10,
  "totalPages": 1
}
```

### Создание события

Дата начала не может быть в прошлом. При обновлении эта проверка применяется только при изменении `startAt`, поэтому название и описание уже начавшегося события можно исправить.

Название ограничено 200 символами, описание — 2000. Ограничения действуют при создании и обновлении; превышение возвращает `400 Bad Request`. В новой схеме БД эти длины закреплены через Fluent API, а строковое представление статуса брони ограничено 20 символами.

Контроллеры передают токен отмены HTTP-запроса в сервисы, запросы EF Core, сохранение и ожидание семафора. Компенсация ошибки фоновой обработки выполняется независимо от отмены запроса.

`POST /events`

```json
{
  "title": "Воркшоп по ASP.NET Core",
  "description": "Практика разработки Web API.",
  "startAt": "2026-09-19T11:00:00Z",
  "endAt": "2026-09-19T14:00:00Z",
  "totalSeats": 30
}
```

Передавайте даты в UTC с суффиксом `Z`: PostgreSQL-провайдер хранит их в `timestamp with time zone`.

`totalSeats` обязателен и должен быть больше нуля. Успешный ответ содержит созданное событие, поля `totalSeats` и `availableSeats` с одинаковым начальным значением, а также заголовок `Location` со ссылкой на событие:

```text
Location: /events/{id}
```

### Обновление события

`PUT /events/{id}`

Тело запроса содержит `title`, `description`, `startAt` и `endAt`. Общее и доступное количество мест при обновлении события сохраняется.

## Бронирования

### Модель брони

| Поле | Тип | Описание |
|---|---|---|
| `id` | `Guid` | Уникальный идентификатор брони |
| `eventId` | `Guid` | Идентификатор события |
| `status` | `BookingStatus` | Текущий статус обработки |
| `createdAt` | `date-time` | Дата и время создания в UTC |
| `processedAt` | `date-time` или `null` | Дата и время завершения обработки в UTC |

Возможные статусы:

- `Pending` — бронь создана и ожидает обработки;
- `Confirmed` — бронь подтверждена;
- `Rejected` — бронь отклонена.

В JSON статусы представлены числовыми значениями перечисления: `0` — `Pending`, `1` — `Confirmed`, `2` — `Rejected`. В PostgreSQL статус хранится строкой через Fluent API-конвертацию.

### Создание брони

`POST /events/{id}/book`

Сервер проверяет наличие места, уменьшает `availableSeats`, создаёт бронь в статусе `Pending` и сохраняет оба изменения одним вызовом `SaveChangesAsync`. Успешный ответ — `202 Accepted`. Общий `SemaphoreSlim` синхронизирует резервирование и возврат мест внутри одного процесса приложения. Заголовок `Location` содержит адрес для получения актуального состояния брони:

```text
Location: /bookings/{bookingId}
```

Пример тела ответа:

```json
{
  "id": "e561b004-68ae-4f90-9228-df08fc496cd2",
  "eventId": "66a1ed2f-a302-4441-a228-559f328bbe5e",
  "status": 0,
  "createdAt": "2026-09-19T08:00:00Z",
  "processedAt": null
}
```

### Получение брони

`GET /bookings/{id}`

Возвращает текущее состояние брони. Сразу после создания статус обычно равен `Pending`, а после фоновой обработки — `Confirmed`.

### Фоновая обработка

Фоновый сервис сразу получает из БД первый пакет идентификаторов броней со статусом `Pending` в отдельном scope и запускает их обработку параллельно через `Task.WhenAll`. После завершения каждого пакета сервис ждёт пять секунд перед следующей выборкой. Каждая задача использует свой scope и `AppDbContext`. Искусственная задержка в две секунды выполняется одновременно для разных броней.

После задержки обработчик повторно проверяет существование события:

- существующая бронь переводится в `Confirmed`;
- если бронь ещё существует, но событие отсутствует, она переводится в `Rejected`; в PostgreSQL целостность связи обеспечивает внешний ключ, а удаление события каскадно удаляет его брони;
- при ошибке этапа обработки бронь переводится в `Rejected`, а зарезервированное место возвращается событию одним вызовом `SaveChangesAsync`;
- ошибки чтения и сохранения при обработке брони также запускают попытку отклонения и возврата места в новом scope; ошибки компенсации журналируются;
- ошибки получения пакета журналируются, после чего фоновый сервис продолжает цикл.

Сервис учитывает отмену приложения через `CancellationToken` и журналирует начало и результат обработки каждой брони. При штатной отмене незавершённая бронь остаётся `Pending` и может быть обработана после следующего запуска.

### Синхронизация

- Сервисы зарегистрированы как scoped и работают напрямую с `AppDbContext`.
- `lock` в модели события защищает проверку и изменение количества свободных мест одного экземпляра сущности.
- `Lock` в модели брони защищает согласованное чтение и изменение `Status` и `ProcessedAt`.
- Общий `SemaphoreSlim` защищает резервирование и возврат мест между экземплярами контекста внутри процесса; он не обеспечивает синхронизацию нескольких экземпляров приложения.
- Отдельный семафор обработчика не допускает пересечения запусков обработки одного набора броней.
- `Task.WhenAll` позволяет фоновому обработчику ожидать параллельно запущенную обработку всех найденных броней.

### Пример сценария

Создайте событие:

```http
POST /events
Content-Type: application/json

{
  "title": "Воркшоп по ASP.NET Core",
  "description": "Практика разработки Web API.",
  "startAt": "2026-09-19T11:00:00Z",
  "endAt": "2026-09-19T14:00:00Z",
  "totalSeats": 30
}
```

Создайте для него бронь:

```http
POST /events/66a1ed2f-a302-4441-a228-559f328bbe5e/book
```

Ответ содержит `202 Accepted`, данные брони и заголовок:

```text
Location: /bookings/e561b004-68ae-4f90-9228-df08fc496cd2
```

Получите состояние брони по этому адресу:

```http
GET /bookings/e561b004-68ae-4f90-9228-df08fc496cd2
```

Первый ответ может содержать `Pending`. Повторный запрос через несколько секунд вернёт `Confirmed` и заполненное поле `processedAt`.

### Пример овербукинга

Создайте событие на три места:

```http
POST /events
Content-Type: application/json

{
  "title": "Событие на три места",
  "description": "Проверка ограничения вместимости.",
  "startAt": "2030-01-01T10:00:00Z",
  "endAt": "2030-01-01T12:00:00Z",
  "totalSeats": 3
}
```

Трижды создайте бронь для полученного `eventId`. Каждый запрос вернёт `202 Accepted`:

```http
POST /events/{eventId}/book
```

Четвёртый такой запрос вернёт `409 Conflict`:

```json
{
  "title": "Booking conflict",
  "status": 409,
  "detail": "No available seats for this event"
}
```

После успешных запросов `availableSeats` события будет равно `0`.

## Тесты

Unit-тесты проверяют сервисы, маппинг сущностей, доменные переходы, защиту от овербукинга, параллельный запуск фоновой обработки, отклонение броней, возврат мест и штатную отмену фонового сервиса.

Тесты используют EF Core InMemory и DI через `ServiceCollection`; каждому тесту выделяется уникальная база, а параллельные запросы выполняются в отдельных scope. PostgreSQL и запущенный API для тестов не нужны. Проверка модели PostgreSQL также выполняется без подключения к серверу; InMemory не проверяет реальные ограничения PostgreSQL.

```powershell
dotnet test --project .\EventManager.Api.Tests\EventManager.Api.Tests.csproj
```

## Валидация

- `title`, `startAt`, `endAt` и `totalSeats` обязательны;
- `title` не может быть пустым или состоять только из пробелов;
- дата окончания должна быть позже даты начала;
- `totalSeats` должно быть больше нуля.

При невалидных данных API возвращает `400 Bad Request`. Если событие или бронь не найдены, API возвращает `404 Not Found`. Ошибки сервисного слоя представлены в формате `ProblemDetails`:

```json
{
  "title": "Request processing failed",
  "status": 404,
  "detail": "Event not found."
}
```

Необработанная ошибка возвращается в том же формате со статусом `500 Internal Server Error`; внутренние детали исключения клиенту не передаются.
